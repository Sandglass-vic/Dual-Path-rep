# pza100：g5/g6 A100 环境

> 返回 [文档索引](README.md)

本分支用于将 DualPath 从原 GAIA DGX H100 环境迁移到 g5/g6 A100 集群。GAIA
Job、Lustre 带宽和 H100 拓扑数据作为历史基线保留；除非明确标注，不能直接用于
pza100。

## 路径

```bash
export CODE_HOME=/data/home/yongxiao/dual-path
export RUNTIME_HOME=/data/home/yongxiao/mydata
export IMAGE_DIR=$RUNTIME_HOME/images
```

g5 的 `/data` 是本地盘，g6 通过 IPoIB NFS 挂载同一目录。代码、镜像、模型和
运行结果因此在两节点可见，但其存储语义和带宽不等同于 GAIA Lustre。

2026-09-17 实测文件系统：

```text
g5 /data: /dev/nvme2n1, XFS, 4 KiB filesystem block
g6 /data: 192.168.10.5:/data, NFSv4.1 over ibs3,
          rsize=1 MiB, wsize=1 MiB, hard, local_lock=none
```

2026-09-29 更新：g5 上唯一的 NFS 连接是 `192.168.11.6 → 192.168.11.5:2049`，g6 已改为
经 CX7 子网的 `ibs4`（`mlx5_1`）挂载，`/etc/exports` 同时导出给 `192.168.10.0/24` 和
`192.168.11.0/24`。CX8（`mlx5_0/4`）子网只承载计算流量和 `ibs3` 上的 IPoIB。
下面 Job 442 / 446 的 g6 数据是在 `ibs3` 挂载时测得的。迁移到 `ibs4` 后，Job 546 /
555 重测 g6 单独 O_DIRECT 读（4 进程 × 4 MiB block，读前清 g5 server cache）为
3.568 / 3.575 GB/s（3.32 / 3.33 GiB/s），与 `ibs3` 时期同量级，挂载参数仍为
NFSv4.1、`rsize=wsize=1 MiB`、`hard`。

实测的带宽、延迟分布和理论上限见 [io-test/RESULTS.md](../io-test/RESULTS.md)
的 pza100 章节（Job 431 / 442 / 446）。要点：g5 本地冷读 6.43 GiB/s（打满 NVMe），
g6 经 NFS 最好只有 3.47 GiB/s = 29.8 Gb/s，即 800 Gb/s 存储网卡的 3.7%，且加并发
无效——瓶颈是 `nconnect=1` 的单条 TCP 连接加上 IPoIB datagram MTU 2044（`ibs3`、
`ibs4` 两端均为 datagram、MTU 2044）。2026-09-29 起 g6 的 KV cache 改走 NFS/RDMA
绕开这一瓶颈，见下一节。

## g6 KV cache 走 NFS/RDMA（2026-09-29）

g5 的 nfsd 早已在 `rdma 20049` 上监听（`/etc/nfs.conf`：`rdma=y`、
`rdma-port=20049`；OFED 的 `rpcrdma`/`svcrdma` 已加载），服务端无需改动。g6 在
`/data`（NFSv4.1/TCP）之外，另挂一个同一导出的 NFS/RDMA 视图：

```text
192.168.11.5:/data  /mnt/nfsrdma  nfs  vers=3,proto=rdma,port=20049,rsize=wsize=1 MiB,hard
```

必须用 NFSv3。v4.1 挂载会先 `EXCHANGE_ID`，发现与现有 `/data` 是同一服务器后把
新挂载合并到已有的 TCP 会话上（session trunking），`/proc/mounts` 显示
`proto=tcp,port=20049`，`nosharecache` 也无效。v3 没有 client-id，挂载得到独立的
RDMA 传输，`/proc/self/mountstats` 中为 `xprt: rdma`。`/data` 本身保持 v4.1/TCP
不动。

### 实测（Job 563，g6 读 g5 同一批文件，每次读前清 g5 server cache，3 轮 median）

| 读法 | TCP `/data` | RDMA `/mnt/nfsrdma` | 单次读 p50 |
|---|---:|---:|---:|
| 逐页：4 rank × 324 个 4 MiB 文件，O_DIRECT | 3.237 GB/s | **5.824 GB/s** | 5.20 → 2.79 ms |
| 大文件：8 进程 × 4 MiB block，O_DIRECT | 3.443 GB/s | **6.931 GB/s** | 9.91 → 4.66 ms |

RDMA 的大文件读已等于 g5 NVMe 本地上限（Job 555：6.95 GB/s），瓶颈从单条 TCP
连接转到盘上。**这只对 g5 server cache 为冷成立**：Job 563 每次读前都清了 server
cache。真实负载里 Decode 读的是自己刚经 NFS 写回、仍在 g5 page cache 中的 KV，
nfsd 以 buffered 方式直接从内存返回，客户端 O_DIRECT 管不到这一层；Job 580–582
的 Decode L3 读因此达到约 20 GB/s，见"L3 读取默认方案与限速"。本组读缓冲为 pageable 内存、无 staging 拷贝；使用 pinned 内存 +
torch staging 的同形态读（Job 559，TCP）为 2.04–2.10 GB/s，两组 TCP 数值不能直接
比较，pinned 内存在 RDMA 上的表现尚未单独测。结果：
`io-test/results/g6-nfs-rdma-ab-563/`，入口 `scripts/smoke/g6_nfs_rdma_ab.sbatch`。

### 挂载管理：`scripts/pza100-nfsrdma.sh`

在 g6 上运行（`ssh g6`；mount/unmount 使用 sudo）：

```bash
scripts/pza100-nfsrdma.sh mount     # 加载 rpcrdma 并挂载；已挂载时不重复
scripts/pza100-nfsrdma.sh status    # 不需要 root；NFSRDMA_ACTIVE 且退出码 0 即正常
scripts/pza100-nfsrdma.sh unmount   # 仍有进程使用时拒绝，并列出 PID
```

该挂载没有写入 `/etc/fstab`，平时保持挂载即可：

| 时机 | 操作 |
|---|---|
| g6 重启后、跑 Decode 在 g6 上的实验之前 | `mount` |
| g5 重启、NFS server 重启、修改 `/etc/exports`、IB/CX7 维护之前 | 先停 Decode/client，再 `unmount` |
| 不再使用 RDMA | `unmount` |

hard 挂载在服务端或链路中断时会让所有访问进程挂起直到恢复，这是维护前卸载的
原因。在 g5 上执行 `mount` 会被拒绝（`/data` 是本地 XFS）。

### PD 运行：`DUALPATH_NFS_RDMA`

`scripts/pd_benchmark.sh` 在 `/data` 为 NFS 的节点（g6）上，把
`$RUNTIME_HOME/test/<alloc>/pd-servers/kv-cache` 整棵目录从
`/mnt/nfsrdma/...` 绑定到容器内的同一路径，引擎、`pd_runtime.sh` 和 L3 路径均不变：

| 取值 | 行为 |
|---|---|
| `auto`（默认） | `pza100-nfsrdma.sh status` 为 active 时启用，否则回落 TCP 并打印 `nfs_rdma=off` |
| `1` | 必须启用，未挂载时报错退出 |
| `0` | 保持 NFS/TCP |

- 覆盖的是整个 `kv-cache/`，包括 L3 文件 `file/` 与 Decode 写回完成标记 `l3-sync/`。
  同一节点上两个 NFS 客户端缓存不能及时看到对方新建的文件，所以 g6 上的 Decode
  与 client 必须走同一视图；覆盖对 g6 上所有角色生效。
- 启用时打印 `nfs_rdma=on kv_cache=... via /mnt/nfsrdma/...`，未显式设置
  `STORAGE_TOPOLOGY` 时 `run.json` 记为 `g5-xfs-export-g6-nfs-rdma`，用于区分新旧结果。
- 模型、日志和结果目录仍走 `/data`；g5 上的 Prefill 不受影响。
- 挂载状态是节点本地的：从 g5 以 `DUALPATH_HOSTNAME=g6` 启动时，脚本用一个 1 CPU 的
  overlap step 在 g6 上探测 `/data` 类型与 `pza100-nfsrdma.sh status`，并在 g6 上建
  目录。Job 576–578 用的是修复前的版本，探测落在 g5 上而被跳过，实际走 NFS/TCP；
  其结果目录已改名为 `*-nfstcp-*`。`DUALPATH_NFS_RDMA=1` 时探测失败会直接退出。
- `pd-servers/decode-0.log` 由 g6 经 NFS 写入，Decode 进程退出前 g5 上可能读到不完整
  的尾部。后处理（`pd_plot.sh`）要在停止 Decode 之后运行，否则会报
  `missing TTFT V3 sides: ... decode=0`。
- 已验证：g6 容器内 `kv-cache` 路径为 `proto=rdma` 挂载，`DUALPATH_NFS_RDMA=0` 与
  g5 的 dry run 不含覆盖挂载。尚未在 NFS/RDMA 上跑过完整 PD 实验；首次运行时应
  检查 Decode 日志中没有 `failed to retrieve page`，并确认 Decode 单页读取时间
  低于 TCP 下的约 13.6 ms。

因此当前 HiCache L3 是 SGLang POSIX `file` backend，物理拓扑为“g5 本地 XFS、
g6 NFS client”，不是 Lustre。历史日志和 patched SGLang 中的 `lustre_*` timing
字段名暂时保留兼容性，但在 pza100 上只表示通用文件读取时间，不能解释为 Lustre
带宽。`DUAL_PATH_O_DIRECT_READ` 默认关闭；启用时启动脚本会在实际 cache 目录执行
对齐的 O_DIRECT read probe，因此 XFS、NFS 和历史 Lustre 均按当前内核与挂载的
真实能力决定是否可用。`lfs getstripe`、OST stripe 和 LNet rail 等 GAIA 设置
不适用于 pza100。

## L3 读取默认方案与限速（2026-09-29）

### 默认方案

| 项 | 默认值 | 说明 |
|---|---|---|
| Prefill（g5）L3 读 | buffered（`DUAL_PATH_O_DIRECT_READ=0`） | 直接读 g5 page cache |
| Decode（g6）L3 读 | NFS/RDMA + buffered（`DUALPATH_NFS_RDMA=auto`） | 需先 `pza100-nfsrdma.sh mount` |
| L3 读限速 | 不限（`DUALPATH_L3_READ_BPS=0`） | 可设 0–20 GB/s |
| 镜像 | `...-dualpath-patched-l3bps-20260929-nich2d-async-kvtrans-hostpin.sqsh` | 含限速、NIC H2D、KVTRANS 补丁 |

为什么不再默认 O_DIRECT：g5 既是 Prefill 节点又是 NFS server，O_DIRECT 在两条
路径上的语义不对称。Prefill 本地 O_DIRECT 一定读 NVMe（约 7–8 GB/s）；Decode 的
O_DIRECT 只绕过 g6 client cache，g5 上的 nfsd 仍以 buffered 读，命中 page cache
时约 20 GB/s（Job 580–582）。GAIA 上 Prefill 与 Decode 都是远端 Lustre client，
不存在这种不对称。改为两端都读 page cache 后，介质一致，存储带宽差异由
`DUALPATH_L3_READ_BPS` 显式模拟。

注意 Decode 不开 O_DIRECT 时，还可能命中 g6 自己的 NFS client cache（它刚写回的
KV），这比读 g5 cache 更快；开启限速后两者都会被限到同一上限。

### `DUALPATH_L3_READ_BPS`

单位 bytes/s，整数，范围 `[0, 20000000000]`，0 表示不限；三端（Prefill、Decode、
client）应设相同值，`run.json` 记录为 `l3_read_bps`（取 client 端环境）。

```bash
common="ALLOC_JOB_ID=<id> DUALPATH_L3_READ_PATH=dynamic DUALPATH_NFS_RDMA=1 DUALPATH_L3_READ_BPS=6000000000 CONTEXT_LENGTH=32768"
env $common scripts/pd_benchmark.sh prefill
env $common DUALPATH_HOSTNAME=g6 scripts/pd_benchmark.sh decode
env $common DUALPATH_HOSTNAME=g6 DATASET=32K AGENTS=4 REPETITION=1 TASK_NAME=<task> scripts/pd_benchmark.sh client
```

实现（`scripts/infra/patch_sglang_benchmark_timing.py` 的
`write_l3_throttle_helper` / `patch_l3_read_throttle`）：

- 限速是**每个 engine** 的 L3 读带宽，与图中 L3 读带宽同一口径（全部 TP rank 的
  字节 ÷ 读窗口）；每个 TP rank 按 `BPS / tp_size` 自行节流。
- 在 `cache_controller._generic_page_get()` 的 O_DIRECT 逐页 `get()` 与 buffered
  `batch_get()` 之后按虚拟时钟补足时间；sleep 位于 `lustre_read` 计时窗口内，
  所以报告的 L3 读带宽即为限速后的值，scatter/staging 不受影响也不计入。
- 不为空闲期积累额度，只允许 2 ms 裕量吸收 sleep 唤醒延迟；请求在空闲后到达也
  不会超出限速突发。模拟 128 × 4 MiB、TP4、每页 0.3 ms 读耗时的单元测试：
  限 1 / 3.5 / 6 / 12 / 20 GB/s 实测 1.00 / 3.51 / 6.03 / 12.13 / 20.37 GB/s。
- 与介质无关：page cache、NVMe、NFS/TCP、NFS/RDMA 均适用。它模拟的是给定带宽的
  存储，而不是真正约束存储本身。
- 限速值高于该路径的实际能力时不起作用（例如 Decode 走 NFS/TCP 时约 1.2–2 GB/s）。

为什么不用 cgroup/网络手段：`io.max` 只限制落到块设备的 IO，page cache 命中不经过
块设备；nfsd 是 root cgroup 中的内核线程，无法放入 job cgroup；`tc` 只作用于 TCP/IP，
RDMA 走 verbs 绕过内核协议栈；降低 IB 端口速率只有少数固定档位且影响整张卡。

### 热读实测（Job 584，`scripts/smoke/g5_g6_hot_read.sbatch`）

引擎同款读法（TP4 × 324 页 × 4 MiB，pinned + torch staging），两套互不重叠的数据
均预热在 g5 page cache；g5 本地 buffered，g6 经 NFS/RDMA O_DIRECT；3 轮 median：

| 场景 | 节点 | 端到端 GB/s | 文件 I/O GB/s | 单页读 p50 |
|---|---|---:|---:|---:|
| 单独 | g5 | 24.15 | 51.9 | 0.29 ms |
| 单独 | g6 | 13.68 | 21.5 | 0.63 ms |
| 同时 | g5 | 22.73 | 48.0 | 0.31 ms |
| 同时 | g6 | 13.55 | 21.7 | 0.63 ms |

"文件 I/O"与引擎的 L3 读带宽同一口径：g6 的 21.5 GB/s 与 Job 581/582 的 Decode
L3 读 20.0–20.4 GB/s 吻合。同时读合计约 36 GB/s，互相影响 1–6%。每次读仅 5.4 GB
（0.24–0.40 s），同时读的重叠覆盖了 g5 全程但只覆盖 g6 约 60%，g6 的干扰可能被
低估。结果：`io-test/results/g5-g6-hot-read-584/`。

  g6 KV cache 走 NFS/RDMA（`DUALPATH_NFS_RDMA=auto`），不限速
  （`DUALPATH_L3_READ_BPS=0`），见"L3 读取默认方案与限速"；
- runtime/model/result 根目录为 `/data/home/yongxiao/mydata`；
- Mooncake rank 映射为 GPU0/1→`mlx5_0`、GPU2/3→`mlx5_4`；
- 调试默认 context length 为 4096。

allocation 配置只保存节点角色、资源、TP size、共享路径和默认镜像。实验参数不写入
allocation env；启动 Prefill、Decode 和 client 时分别指定，并且三端需要保持一致。
这包括 `DUALPATH_L3_READ_PATH`、`DUAL_PATH_O_DIRECT_READ`、`ABLATION_PROFILE`、
context length、HiCache/Host staging 和 timing 参数。`TP_SIZE` 默认固定为 4，
与 allocation 的 GPU 资源一起保存，不能在单个角色启动时覆盖。显式运行参数在
加载 allocation env 后仍具有最高优先级。

### 启动方式：不要嵌套 srun

`pd_benchmark.sh prefill|decode` 本身会按 allocation 配置启动 engine step：

```bash
srun --jobid="$ALLOC_JOB_ID" --exclusive ... \
  --cpus-per-task=192 --gres=gpu:4 --mpi=none ... \
  bash scripts/tests/runtime/pd_runtime.sh <role> <id>
```

因此它必须直接在 allocation shell 中运行，不能再用一个更小的外层 step 包住。
Allocation 544 中 Decode 的启动方式是：

```bash
srun --cpus-per-task=1 ... bash -lc '... scripts/pd_benchmark.sh decode'
```

外层 task 只有 1 个 CPU，内层 engine step 却要求 192 个 CPU，Slurm 报告：

```text
srun: Job step's --cpus-per-task value exceeds that of job (192 > 1)
srun: Job step may never run.
```

这是嵌套 srun 的资源规格冲突，与 Decode 模型或 Mooncake 无关。之前这种写法有时
仍能继续运行，是因为 Slurm 允许了部分 overlap，但结果不可靠，并且外层 step 退出后
会留下残留 engine 进程。

正确流程：

1. `scripts/pd_alloc.sh 1 1` 进入 allocation shell；
2. 在对应节点的 allocation shell 中直接运行 `scripts/pd_benchmark.sh prefill` 或
   `scripts/pd_benchmark.sh decode`（加上三端一致的 `DUALPATH_L3_READ_PATH` 等参数）。

如果必须从登录节点自动化启动，外层 srun 至少按 engine 资源申请：

```bash
srun --jobid="$ALLOC_JOB_ID" --overlap \
  --nodes=1 --ntasks=1 --nodelist=g6 \
  --cpus-per-task=192 --gres=gpu:4 --mpi=none \
  bash -lc 'cd /data/home/yongxiao/dual-path && ...'
```

更稳妥的是让自动化入口直接启动 `scripts/tests/runtime/pd_runtime.sh`，不再经过
`pd_benchmark.sh` 的第二层 engine srun。

Allocation 573/574（2026-09-29，NFS/RDMA）又因同样的包装（sbatch 内
`srun --overlap --cpus-per-task=1 ... pd_benchmark.sh prefill|decode`）作废：Slurm
只打印 `exceeds that of job (192 > 1)` 警告后照常运行，engine 挤在外层 step 的 CPU
上，TPOT 从 24–26 ms 变为 606–823 ms，g5 Prefill 计算从 0.3 s 变为 1.3–1.9 s，
wall time 4586–6090 s。L3 读并未卡住（Decode 2.85 GB/s、Prefill 5.07 GB/s）。

`pd_benchmark.sh` 现在会拒绝这种启动：当 `SLURM_JOB_ID` 等于目标 allocation 且
`SLURM_CPUS_PER_TASK` 小于该角色所需 CPU（engine 192、client 8）时报
`Refusing to launch ...` 并退出。allocation shell、g5 登录 shell 和属于其他作业的
shell 不受影响。

### 已验证的运行方式（Allocation 557，2026-09-29）

不需要 ssh 或外层 srun，所有角色都可以从 g5 登录 shell 启动。`pd_benchmark.sh`
发起的 engine/client step 本来就带 `--nodelist`，`DUALPATH_HOSTNAME` 只决定
脚本按哪个节点解析角色：

```bash

  --cpus-per-task=192 --gres=gpu:4 --mem=0 --exclusive --time=02:30:00 \

SLURM_JOB_ID=<id> SLURM_JOB_NODELIST='g[5-6]' PREFILL_NODES=1 DECODE_NODES=1 \
  CLIENT_PLACEMENT=decode ENGINE_GPUS=4 TP_SIZE=4 ENGINE_CPUS=192 CLIENT_CPUS=8 \
  PD_ALLOCATION_NO_SHELL=1 PD_KEEP_ALLOCATION_ENV=1 \
  bash scripts/pd_alloc.sh __allocation_shell

# 1b. 确认 g6 的 NFS/RDMA 挂载（默认方案需要；见"g6 KV cache 走 NFS/RDMA"）
#     ssh g6 'cd /data/home/yongxiao/dual-path && scripts/pza100-nfsrdma.sh mount'

# 2. 三端参数一致；g6 上的角色用 DUALPATH_HOSTNAME=g6 从 g5 发起。
#    默认方案：两端 buffered + g6 走 RDMA；限速按需加 DUALPATH_L3_READ_BPS。
common="ALLOC_JOB_ID=<id> DUALPATH_L3_READ_PATH=prefill DUALPATH_NFS_RDMA=1 DUALPATH_L3_READ_BPS=0 CONTEXT_LENGTH=32768"
env $common scripts/pd_benchmark.sh prefill                               # g5
env $common DUALPATH_HOSTNAME=g6 scripts/pd_benchmark.sh decode           # g6
env $common DUALPATH_HOSTNAME=g6 DATASET=32K AGENTS=4 REPETITION=1 \
  TASK_NAME=<task> scripts/pd_benchmark.sh client                          # g6

# 3. 停止顺序 client → Decode → Prefill（各 Ctrl-C 一次），然后清 KV
rm -rf $RUNTIME_HOME/test/<id>/pd-servers/kv-cache
```

注意：

- 默认镜像 `l3bps-20260929` 在 `DUALPATH_L3_READ_BPS=0` 时与
  `dynamic-20260919`（Job 517/518、557、576–582 所用）行为一致；要逐字节复现旧
  结果时可显式传 `IMAGE=...-dynamic-20260919.sqsh`（该镜像不支持限速）。
- 若要复现 Job 557/576–582 的 O_DIRECT 结果，三端加 `DUAL_PATH_O_DIRECT_READ=1`。
- 32K 轨迹必须设置 `CONTEXT_LENGTH=32768`。
- 服务端日志以追加方式写入 `pd-servers/{prefill,decode}-0.log`，判断 ready 时要看
  本次启动之后的 `fired up and ready`。
- Ctrl-C 后 engine 若在 32 秒内未退出，Slurm 会以 SIGKILL 结束 step（退出码
  137）。只要 client 已完成、Decode 的 L3 写回已结束，这不影响结果。
- 切换 `DUALPATH_L3_READ_PATH` 必须重启两个 server，并清空 KV 保证 cold start。

### 8-agent、8 GB/s、显存比例调整验证（Jobs 590–592，2026-09-29）

下面是一组已经实际完成的 32K、8-agent、1 repetition 端到端验证。三种 path
分别使用独立的 g5/g6 allocation，并按 Prefill、Decode、Dynamic 顺序串行提交；
后一个 job 使用前一个 job 的 `afterany` 依赖。每个 allocation 均为独占双节点，
避免不同实验共享 page cache 或 GPU/CPU 资源。

#### Allocation 资源

```bash
opts="-p run -N2 -w g5,g6 --ntasks=2 --ntasks-per-node=1 \
  --cpus-per-task=192 --gres=gpu:4 --mem=0 --exclusive -t 02:00:00"

# 实际提交方式：每个 case 一个独立 allocation；后续 case 等前一个结束

  -o /tmp/dp-l3bps8g-a8-prefill-%j.out /tmp/dualpath-rdma-case.sbatch prefill)

  -o /tmp/dp-l3bps8g-a8-decode-%j.out --dependency=afterany:$j1 \

j3=$(sbatch --parsable $opts -J dp-l3bps8g-a8-dynamic \
  -o /tmp/dp-l3bps8g-a8-dynamic-%j.out --dependency=afterany:$j2 \
  /tmp/dualpath-rdma-case.sbatch dynamic)
```

### IO 测试作业必须独占节点

`run`/`build` 分区为 `OverSubscribe=YES:4`，不独占时两个 IO 作业会被调度到同一
节点并发运行，互相污染带宽（Job 547/548 因此作废）。IO 测试 sbatch 必须带
`--exclusive --mem=0`；`run` 分区 `DefMemPerNode=UNLIMITED`，只写 `--exclusive`
会报 `Requested node configuration is not available`。多个 IO 测试要串行时用
`--dependency=afterany:<jobid>`；`--dependency=singleton` 只对同名作业生效。

### PD 端到端：Prefill 与 Decode path 对比（Allocation 557，NFS/TCP）

32K、4 agents、1 repetition、104 turn、O_DIRECT、`dynamic-20260919` 镜像，
均为 cold start、104/104 turn、无 replay error：

| 场景 | Job | TTFT | JCT | TPOT | L3 读带宽 | L3 读 | 排队 |
|---|---|---:|---:|---:|---:|---:|---:|
| Prefill path，不限速 | 517 | 1.79 s | 211.3 s | 26.0 ms | 8.35 GB/s | 0.59 s | 0.49 s |
| Prefill path，g5 限速 3.5 GB/s（已移除的 cgroup `io.max` 方案） | 557 | 2.62 s | 232.4 s | 25.6 ms | 3.82 GB/s | 1.28 s | 0.67 s |
| Decode path（`ibs4` NFS） | 557 | 11.91 s | 475.7 s | 24.2 ms | 1.22 GB/s | 3.96 s | 7.04 s |
| Decode path（`ibs3` NFS，旧镜像） | 500 | 6.77 s | 337.5 s | 24.4 ms | 1.90 GB/s | 2.56 s | 3.41 s |

初步结论：限速准确生效，但 Prefill path 在 3.5 GB/s 下仍远快于 Decode path。
两条路径的差距主要不是 g5 磁盘带宽，而是 Decode 经 NFS 的小块 O_DIRECT 读在真实
负载下只有约 1.2 GB/s，并由此放大排队。以上 Decode path 均为 NFS/TCP；
NFS/RDMA 下的结果见 Job 580–582（"L3 读取默认方案与限速"一节）。当时 Prefill
的限速用的是 cgroup `io.max`，该方案已移除，现在用 `DUALPATH_L3_READ_BPS`。

- 1P2D、2P2D 无法在本集群复现；
