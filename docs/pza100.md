# pza100：g5/g6 A100 异平台参考

> 返回 [文档索引](README.md)

main 分支的目标平台是 GAIA DGX H100 + Lustre；`pza100` 分支把 DualPath 迁到了
g5/g6 A100 集群。本页只记录**两个平台的差异**和**在 pza100 上得到、对 main 有
参考价值的结论**。pza100 的镜像 SHA、Job 编号和运行入口默认值以 `pza100` 分支
为准，不在此重复。

main 的脚本默认值全部是 GAIA 的，跑 pza100 需要显式覆盖路径、分区、GPU 数、
TP size 和网卡映射。

## 平台差异速查

| | GAIA（main） | pza100 |
|---|---|---|
| 节点 | `dgx-gaia-[09-63]` | `g5`, `g6` |
| 分区 | `GAIA` | `run`（4h）/ `build`（12h） |
| GPU | 8 × H100 80GB | 4 × A100 PCIe 40GB |
| TP size | 8 | 4 |
| CPU/内存 | 112 CPU / ~2 TiB | 192 CPU / ~502 GiB |
| 共享存储 | Lustre `/mnt/lustre` | g5 本地 XFS，g6 经 IPoIB NFS |
| PD HCA | `mlx5_0,3,4,5,6,9,10,11`（8 卡各一） | `mlx5_0`, `mlx5_4`（4 卡共享 2 张） |
| Socket/Gloo 接口 | 自动探测 | 必须设 `ibs3` |
| Enroot | 3.2.0 | 4.2.0 |
| 拓扑 | P + D + 独立 client（3 节点） | 只有 2 节点，client 与 Decode 共置 |

pza100 上需要显式设置，否则 NCCL/Gloo 起不来：

```bash
export NCCL_IB_HCA=mlx5_0,mlx5_4
export NCCL_NET_GDR_LEVEL=PIX
export NCCL_SOCKET_IFNAME=ibs3
export GLOO_SOCKET_IFNAME=ibs3
```

GPU0/1 邻近 `mlx5_0`，GPU2/3 邻近 `mlx5_4`，Mooncake 映射为
`{"0":"mlx5_0","1":"mlx5_0","2":"mlx5_4","3":"mlx5_4"}`。

## 存储：两侧不对称

这是 pza100 与 GAIA 最本质的区别，也是多数结论不能互搬的原因。

```text
g5 /data: /dev/nvme2n1, XFS, 4 KiB block          （本地盘）
g6 /data: 192.168.10.5:/data, NFSv4.1 over ibs3   （经 g5 导出）
          rsize=1 MiB, wsize=1 MiB, hard, local_lock=none
```

实测（详见 [io-test/RESULTS.md](../io-test/RESULTS.md) 的 pza100 章节）：g5 本地
冷读 6.43 GiB/s 打满 NVMe，**g6 经 NFS 最好只有 3.47 GiB/s**，即 800 Gb/s 存储
网卡的 3.7%，且加并发无效——瓶颈是 `nconnect=1` 的单条 TCP 连接加上 IPoIB
datagram MTU 2044。

因此 pza100 的两个引擎看到的存储能力相差近一倍，而 GAIA 上两侧都直连 Lustre、
带宽几乎相同（7.59 vs 7.58 GB/s）。

L3 用的是 SGLang POSIX `file` backend。patched SGLang 里的 `lustre_*` timing 字段
在 pza100 上只表示通用文件读取时间，`lfs getstripe`、OST stripe 和 LNet rail 等
GAIA 设置一概不适用。

## 对 main 有参考价值的结论

**dynamic read path 的收益取决于两侧存储对称性，不是策略本身的属性。**

同样的 `alternate_per_turn`，两个平台结论相反：

| | pza100（TP4，Decode 侧走 NFS） | GAIA（TP8，两侧直连 Lustre） |
|---|---|---|
| 静态 Prefill TTFT | 1.874 s | 4.135 s |
| 静态 Decode TTFT | 6.771 s | 4.407 s |
| Dynamic TTFT | 6.471 s | **1.657 s** |
| 结论 | 明显劣于静态 Prefill | 快 2.49x |

pza100 上 Decode 侧读取要穿 NFS，两侧不对等，把一半请求分过去反而被慢的那侧拖
住；dynamic 的平均 TTFT 因此贴近静态 Decode（6.471 vs 6.771），而非两者之间。
GAIA 上两侧对称，分摊才产生收益。详见
[dualpath-path-comparison.md](dualpath-path-comparison.md)。

pza100 的 dynamic 验收本身是通过的：allocation `502` 完整跑完 104/104 turn，两侧
日志对 104 个 request 的 resolved path `0 mismatch`，每条 trajectory 严格按 turn
交替、相邻 trajectory 反相，非 owner 侧 L3 read tokens 为 0。**选路机制正确，是
拓扑不划算。**

**A100 40GB 需要绝对 host pool 尺寸，H100 80GB 不需要。** prefetch 配额是
`0.8 × (host pool − device pool)`，A100 上 device pool 小，ratio 派生的配额会塌到
约 26k tokens，比单个 32K 前缀还小；H100 上反而是绝对值 40 GB 更小。两个平台的
取值方向相反，见 [dualpath-fixes.md](dualpath-fixes.md) 缺陷 3。

## 当前限制

- 集群只有两个节点，1P2D / 2P2D 无法复现；
- H100 80GB 的 KV、HiCache 和 Host staging 参数不能直接沿用到 A100 40GB；
- GAIA 的历史 Job、Lustre 带宽和 H100 拓扑数据不适用于 pza100，反之亦然。
